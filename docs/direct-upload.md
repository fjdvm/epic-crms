# Shared direct uploads (#233)

`features/files/client.ts` exports `uploadFile(module, file, { ticketId })`. The browser sends only metadata to `requestFileUpload`, PUTs the File directly to the storage-signed URL without credentials, then calls `confirmFileUpload` with its pending reference. No File or Blob is passed to a Server Action. The server confirms metadata and downloads the original from storage, with a bounded read, to check actual size and detect MIME using `file-type`. This is signature detection, not antivirus scanning or complete media decoding.

Tickets accepts JPEG, PNG (including APNG), GIF, WebP, PDF, MP4 and MOV, from 1 byte through 25 MiB. Invalid bytes are refused and deleted. Failed deletion is explicitly reported as `cleanupFailed`; the upload is never returned as ready. A failed storage request reports unavailability rather than pretending the operation succeeded. Pending uploads use file-storage's existing expiration lifecycle.

All actions check the owning Module on the server. References are HMAC signed, bind the Module, uploader, metadata, Ticket context and phase, and expire after 30 minutes (pending) or 60 minutes (ready). References are opaque application tokens, not encrypted secrets. A bare File id is not accepted from a browser. `getFileView` rechecks the Module for each view; `viewStoredFile` is for internal record loaders using a File id read from an authorized record. Ticket and Conversation loaders use that protected adapter. Gateway requests carry the server-only Caller key; signed storage reads and browser PUTs do not.

Ticket actions `reply` and `openNewTicket` accept a ready reference in FormData field `attachment`. For replies, upload with that Ticket's id; for a new Ticket, use `{ ticketId: null }`. The action proves the same uploader and context, checks active private permanent storage metadata, then stores the existing `ticket_messages.file_id` and links the File to the Message. An attachment cannot be combined with the legacy `image` field. A refused or uncertain Message save does not delete an already confirmed File, which could already be attached to a saved Message. Valid uploads abandoned before saving remain permanent; this feature does not introduce draft garbage collection.

The picker and PDF/video rendering belong to #237; existing image forms continue to work until that integration. Migration of other record upload paths belongs to #238. Shared policies are private/permanent for Tickets, public/permanent for Marketing, and private/temporary for Fulfilment and Returns; those other consumers currently accept images only and retain their existing paths.

## Configuration and deployment

No database migration or new database role is required: Message File ids already exist, and references are stateless. Node 22 or newer is required by `file-type` 22. Configure `CREOMS_GATEWAY_URL`, `CREOMS_GATEWAY_CALLER_KEY`, and a signing secret of at least 32 characters. `CREOMS_UPLOAD_SECRET` is optional and falls back to `CREOMS_SERVICE_SECRET` when absent or empty. Rotating the chosen signing key expires outstanding references. Never expose these keys via `NEXT_PUBLIC_` variables. Storage CORS must permit the app origin's PUT requests and Content-Type header.

Tests use an in-process HTTP file-storage fake and the real Server Actions, plus a throwaway PostgreSQL-compatible database for Message writes. They cover a browser-directed 6 MiB PUT, 25 MiB boundary, actual image/video/PDF signatures, mismatch deletion and deletion failure, bounded reads, malformed/expired/foreign references, Module revocation, claim races and protected Message views. Live gateway/bucket verification requires deployment credentials and browser CORS access; it is separate from the fake tests.
